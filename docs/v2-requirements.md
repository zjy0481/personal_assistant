# V2 需求文档

> 状态：已确认（V2 需求基线）
> 基线：V1 日报助手
> 创建日期：2026-08-29
> 关联 Issue：#14、#15、#16、#17、#18、#19

## 0. 已确认决策摘要

- V2 分三阶段交付：网页端 + LLM 摘要/问答 → 企业微信智能机器人 + 极端天气预警 → 收藏 + 数据可视化。
- V2 保持单用户，数据表预留 `user_id`；使用腾讯云轻量应用服务器运行独立服务进程。
- 前端采用独立 React + Vite + Tailwind + ECharts；FastAPI 提供 API，现有 Jinja 页面为迁移期兼容入口。
- 数据库继续使用 SQLite，并引入规范化表与稳定 `item_id`；保留日报快照可回放。
- LLM 使用 DeepSeek 官方 API，模型为 `deepseek-v4-flash`；统一 `LLMClient`，设置每日/每分钟调用上限和失败熔断。
- 企业微信使用智能机器人长连接接收群聊提问，保留现有 Webhook“日报”做推送与显式 @ 提醒。
- 极端天气使用免费公开源轮询（主源为中央气象台/中国天气网，备用源为和风天气免费 API），每 10 分钟一次；预警仅首次发布和等级升级时推送。
- 收藏仅针对新闻、AI 要事、GitHub 项目条目；可视化仅保留新闻热词与 GitHub 热度，不做天气趋势。
- 日报、趋势、预警默认保留 180 天；收藏永久保留；问答会话保留 7 天。
## 1. 背景与目标

V1 已经完成单用户每日日报，覆盖天气、时事新闻、GitHub 热门、AI 领域要事，使用同一份日报快照，并通过 PushPlus 推送、企业微信群机器人备用推送、网页端展示。

V2 的目标不是简单增加功能，而是把网页端从“静态展示页”升级为“可交互的个人信息入口”：

1. 重建美观、响应式的网页端，作为聊天、收藏、图表等交互能力的承载层。
2. 引入可配置的语言模型服务，为日报内容条目生成中文简介，并在网页端提供日报问答。
3. 在企业微信群聊中通过智能机器人接收 `@` 提问，由同一套 LLM 服务回答。
4. 针对配置地区持续监测极端天气预警，并主动追加推送，不受每日 08:00 限制。
5. 支持用户在网页端收藏新闻、文章和 GitHub 项目。
6. 以图表展示新闻热词变化和 GitHub 榜单热度变化（不做天气趋势）。

V2 仍保持单用户边界，并继续遵守“网页端与推送端共享同一份日报快照”的 V1 原则。

## 2. V2 术语补充

### 语言模型服务（LLM Service）

一个可配置的、负责调用外部语言模型完成摘要和问答的独立服务边界。网页端问答与企业微信问答必须复用该服务，不允许各自私接不同模型。

### 日报问答（Report Q&A）

用户针对某一日报快照提出自然语言问题，系统先检索相关内容块或内容条目，再将上下文交给语言模型，返回带来源引用的中文回答。

### 企业微信智能机器人（WeCom AI Bot）

企业微信中开启 API 模式的智能机器人，不是只能发送消息的“群机器人 Webhook”。它支持群聊 `@` 触发、消息回调、主动回复以及流式回复。

> 纠错：V1 的“企业微信群机器人 Webhook”只支持向群聊发送消息，不能接收群聊消息，因此无法直接实现“用户 @ 机器人提问、机器人回复”。V2 必须改用企业微信智能机器人。

### 极端天气预警（Extreme Weather Alert）

由气象部门发布、具有地区、类型、等级、发布时间和来源的可追踪预警事件，例如台风、暴雨、高温、寒潮、大风、雷电、大雾。它不是每日日报的普通内容条目，需要独立监测、去重和推送。

### 内容条目标识（Content Item ID）

用于跨日报稳定识别同一篇新闻、同一篇文章或同一个 GitHub 项目的标识。V1 只有 URL/标题去重，V2 的收藏、摘要、问答引用和趋势聚合都需要稳定 ID。

### 趋势快照（Trend Snapshot）

按日报日期聚合后保存的指标记录，例如当日温度、新闻关键词 Top N、GitHub 仓库 star 数。趋势页优先读取趋势快照，不直接实时调用外部数据源。

### 收藏（Favorite）

用户主动保存的一条内容条目，包含条目引用、收藏时间及可选备注。V2 默认单用户，但数据表应预留用户维度的扩展空间。

## 4. 详细需求

### V2-01 美观前端与交互 API

#### 现状

- 当前为 FastAPI + Jinja2 服务端渲染。
- 页面只有基础 HTML，导航、卡片、间距、移动端适配和状态提示均不完善。
- 旧页面直接读取 JSON 快照，没有可供前端交互的 API。

#### 目标

- 网页整体美观、信息层级清晰、支持桌面与手机。
- 首页作为仪表盘，展示运行状态、预警提示、各内容板块摘要。
- 后续可以承载收藏、日报问答和趋势图表。

#### 方案建议

1. 新增独立前端应用，推荐 React + Vite + Tailwind，图表优先 ECharts，使用 build-web-apps 插件辅助视觉设计与前端搭建。
2. FastAPI 继续作为后端，新增 `/api/...` 接口；前端通过 API 获取数据，不再由 Jinja 承担主要页面渲染。
3. 现有 Jinja 模板保留为迁移期的兼容页面，迁移完成后可以归档。
4. 保持 token 鉴权，并明确前端如何安全保存凭证。
5. 使用统一的加载、空数据、降级和错误状态组件。

#### 验收标准

- 首页、天气、新闻、GitHub、AI、收藏、问答页面在 1280px 与 375px 宽度下无布局溢出。
- 页面支持清晰的中文排版、统一的导航与主题风格。
- 数据接口、鉴权、健康检查与现有 `/health` 行为不回归。
- 无数据、部分降级、接口失败均有用户可见的提示。
- 控制台无未处理错误，关键流程可通过自动化测试。

### V2-02 LLM 中文简介与网页问答

#### 现状

- 新闻和 AI 要事使用 RSS 原始摘要，GitHub 使用项目描述。
- 摘要可能为英文或未清洗的 HTML，网页没有统一的中文解释。
- 没有聊天接口、对话历史或稳定的条目引用能力。

#### 目标

- 为新闻、AI 要事、GitHub 项目等内容条目提供 1–3 句中文简介。
- 用户在网页端可以就最新日报提问，回答附来源。
- LLM 失败时不影响日报生成、保存和推送。

#### 方案建议

1. 抽象 `LLMClient`，支持 OpenAI 兼容接口，配置 `provider`、`base_url`、`api_key`、`model`、`timeout`、`retry` 和调用上限。
2. 在 `ContentItem` 上增加 `llm_summary`、`summary_status`、`summary_model`，并持久化。
3. 日报生成时批量生成摘要；失败后保留原摘要并标记 `not_generated`，允许重试。
4. 新增日报检索和问答服务，提供 `POST /api/chat`；回答必须给出条目 URL 或来源标识。
5. 限制上下文长度、单次请求量和每日调用量，并记录失败原因。
6. 天气的当前值、未来几天属于结构化天气字段，不是普通内容条目；若用户希望有整段中文天气说明，可作为独立的“天气概要”服务处理。

#### 验收标准

- 新闻、AI 要事、GitHub 项目条目均能显示中文简介或明确的未生成状态。
- 简介不虚构事实，不伪造来源，并保留原文链接。
- 网页问答返回中文，涉及日报事实时给出对应条目引用。
- LLM 超时、限流或配置缺失时日报仍可生成和推送。
- API Key 不出现在网页、日志或前端代码中。

#### 待决策

- LLM 提供方、模型与调用成本。
- 摘要生成时机：日报构建时批量生成，还是网页端按需懒加载。
- 日报问答会话是否需要长期保存、是否支持流式输出。

### V2-03 企业微信智能机器人问答

#### 路线纠错

企业微信群机器人 Webhook 只能单向推送，不能接收群聊消息，也不能被 `@` 触发问答。

实现群聊问答需要企业微信“智能机器人”，并开启 API 模式。官方提供两种模式：

| 模式 | 服务器要求 | 复杂度 | 适用场景 |
| --- | --- | --- | --- |
| 设置接收消息回调地址（Webhook） | 公网可访问 URL | 需要 Token/AESKey 加解密 | 已有公网服务的普通回调场景 |
| 长连接（WebSocket） | 无需公网 IP | 需要心跳与断线重连 | 本机、内网、无固定公网 IP |

本项目当前没有公网服务器和域名，因此推荐优先验证“长连接”模式，使用 BotID + Secret 建立连接。

#### 目标

- 用户在群聊中 `@` 智能机器人后，系统调用 LLM 回答。
- 回答引用用户触发消息，并尽量给出来源。
- 支持消息排重、断线重连、频率保护与配置校验。

#### 方案建议

1. 新增企业微信智能机器人入站适配器，负责连接、订阅、心跳、断线重连与消息处理。
2. 配置项包括 `wecom_ai_bot_id`、`wecom_ai_bot_secret`、`wecom_ai_mode`，如选择回调模式还需 Token、EncodingAESKey。
3. 收到 `aibot_msg_callback` 后校验群聊与 `@` 触发，去掉机器人名字再进入共享的 LLM 问答服务。
4. 回复时透传 `req_id`，按官方限制控制频率；记录 `msgid` 防重复。
5. 长连接服务独立进程运行；若复用该通道主动推送预警，需先验证会话已被用户激活。

#### 验收标准

- 群聊中 `@` 智能机器人可得到中文回答。
- 回答引用提问，涉及日报条目时附来源。
- 同一 `msgid` 不重复回复。
- 断线后可自动重连，不会重复订阅。
- 未授权群聊/用户不处理，配置与 LLM 失败均有日志和降级回复。
- 现有 Webhook 日报推送能力不回归。

#### 待决策

- 企业微信管理后台是否可选 `aibot` 权限，以及是否允许创建智能机器人。
- 长连接是否需要引入官方 Aibot Python SDK 或自行维护 WebSocket 客户端。
- 群聊中是否由企业微信自动向提问者显示提醒，还是需要额外验证显式 `@`。

### V2-04 极端天气预警主动推送

#### 现状

- V1 仅在每天 08:00 生成并推送日报。
- Open-Meteo 提供当前天气、未来三天预报和空气质量，但没有中国气象预警的官方覆盖保证。
- 没有预警采集、去重、状态记录和网页预警展示。

#### 目标

- 配置地区出现台风、暴雨、高温等预警时，在分钟级延迟内主动推送。
- 同一预警不重复推送，升级或解除时按规则再次通知。
- 网页天气页展示当前生效预警与历史预警。

#### 方案建议

1. 新增 `WeatherWarningSource` 抽象和 `WeatherAlert` 模型，保存类型、等级、标题、描述、生效时间、解除时间和来源 URL。
2. 优先适配中国气象局/中央气象台等公开预警源；不要仅依赖 Open-Meteo 作为唯一官方源。
3. 新增预警监测任务、去重表和运行状态表，以预警 ID/地区/类型为幂等键。
4. 新增独立 `AlertPushAdapter`，可复用 PushPlus 与现有企业微信群机器人，使用独立预警模板。
5. 明确预警与当日日报快照的关系。建议将预警作为独立事件记录并推送，避免破坏 V1“同日一份不可变快照”的语义；若需要合并到日报，需单独定义快照更新规则。
6. 当前 GitHub Actions 只能按 cron 分钟级运行，无法保证秒级实时。低延迟要求需要常驻进程、云函数或消息队列。

#### 验收标准

- 预警发生后无需等到 08:00 即可推送。
- 推送内容包含类型、等级、地区、发布时间、来源与安全提示。
- 服务重启后不会重复推送同一预警。
- 预警升级、解除可按配置再次推送。
- 预警数据源失败时不影响日报生成，并记录可诊断的降级信息。

#### 待决策

- 预警数据源接口/公开页面稳定性与使用合规性。
- 运行环境：GitHub Actions 分钟任务、云服务器常驻进程或云函数。
- 是否设置夜间静默、预警类型优先级和重复提醒规则。

### V2-05 网页端收藏

#### 目标

- 用户在新闻、AI 要事、GitHub 项目条目上收藏/取消收藏。
- 提供收藏列表页，支持按类型、来源、时间筛选与搜索。
- 收藏持久化，刷新和重启后不丢失。

#### 方案建议

1. 引入稳定 `item_id`，优先使用 URL，缺失 URL 时使用标题、来源与内容块生成，并为历史数据回填。
2. 新增收藏表：`item_id`、`report_date`、`block_kind`、`title`、`url`、`source`、`note`、`status`、`created_at`、`updated_at`。
3. 新增 API：`GET /api/favorites`、`POST /api/favorites`、`DELETE /api/favorites/{item_id}`。
4. 网页端在内容卡片显示收藏按钮，收藏页支持移除、跳转原文和查看来源。
5. 数据表预留 `user_id`，但 V2 默认只服务单用户。

#### 验收标准

- 新闻、AI 要事、GitHub 项目均可收藏与取消收藏。
- 同一条目重复收藏返回幂等结果。
- 刷新页面、重启服务后收藏仍在。
- 收藏页可以查看原文链接、内容类型和收藏时间。
- 鉴权缺失时收藏接口拒绝访问。

### V2-06 数据可视化

#### 目标

- 天气趋势：不在 V2 范围内；仅保留新闻热词和 GitHub 热度。
- 新闻热词：展示高频关键词的每日变化。
- GitHub 热度：展示仓库 star 数、排名和上榜次数变化。

#### 方案建议

1. 优先从已有日报快照和趋势快照聚合，不在每次打开图表时访问外部数据源。
2. 推荐前端使用 ECharts，后端提供日期范围、指标和聚合粒度参数。
3. 时间轴统一使用 `report_date`，避免生成时间时区差异造成口径不一致。
4. 新闻热词引入中文分词（如 jieba）和停用词表，按日计算 Top N；也可作为备选使用 LLM 提取关键词。
5. GitHub 热度以 `owner/repo` 为主键，展示最近 N 天 star 数据、新增量与上榜次数。
6. 天气趋势不做；若后续需要，另立需求，不并入 V2 图表。

#### 验收标准

- 两张图表（新闻热词、GitHub 热度）至少支持最近 7 天，可切换 30 天（数据允许时）。
- 数据量不足、来源降级、查询失败均有明确占位与错误提示。
- 横轴时间、单位、中文显示和移动端缩放正确。
- 历史数据变更后可重新计算或回填。
- 图表请求不直接依赖外部实时 API。

## 5. 总体架构建议

### API-first

FastAPI 继续作为单一后端，网页端通过 `/api` 访问日报、收藏、问答、预警和趋势数据。这样后续接入企业微信或其他客户端时，无需复制业务逻辑。

### 共享 LLM 服务

网页端问答、企业微信问答和中文简介共用 `LLMClient` 和日报检索逻辑，避免不同入口产生不一致的答案。

### 规范化数据存储

V1 的 `report_snapshots.payload` 适合保存完整快照，但不适合收藏、问答和趋势聚合。V2 建议引入：

- `content_items`：稳定 `item_id`、标题、URL、来源、摘要、LLM 简介和首次出现日期。
- `favorites`：用户收藏关系。
- `weather_alerts`：预警事件与推送状态。
- `trend_snapshots`：按日报日期聚合的趋势指标。

日报快照仍保留为不可变、可完整回放的数据；规范化表用于索引、关联和分析。

### 独立事件进程

企业微信长连接和极端天气监测需要持续运行，应作为独立进程或系统任务，与网页服务、每日日报任务分离，避免相互阻塞。

## 6. 范围外

- 多用户账号与权限体系。
- 移动端原生 App、小程序或桌面客户端。
- 自动抓取文章正文、长效记忆与复杂多 Agent 编排。
- 实时行情、股票、任务代办等 V1 已明确不在范围内的能力。
- 社交媒体自动发布、营销推荐或外部平台账号绑定。

## 7. 主要风险

1. LLM 提供方、成本、网络可用性和内容可靠性需要先做小样本验证。
2. 企业微信智能机器人权限、长连接行为与群聊提醒表现依赖真实企业环境，应先做最小闭环验证。
3. 极端天气预警数据源可能只提供公开页面或非稳定接口，需要设计源适配与降级。
4. 当前 GitHub Actions 不适合秒级实时任务，主动推送链路需要确定长期运行方式。
5. 现有 SQLite JSON 快照向规范化数据迁移时，必须保留旧快照可读性，避免历史数据丢失。


## 8. 最终确认决策（优先于正文中的旧草案）

> 本节记录 2026-08-29 用户确认后的结论，是 V2 需求分析和 Issue 同步的依据。正文中仍保留的“待决策”或旧草案仅作为历史背景，在没有冲突时可用于理解需求来源。

### 总体与交付

- V2 分三阶段：第一阶段完成前端重构、LLM 摘要与网页问答；第二阶段完成企业微信智能机器人问答和极端天气预警；第三阶段完成收藏与数据可视化。
- 单用户，但规范化表预留 `user_id`。
- 部署使用腾讯云轻量应用服务器（假设 2 核 2G、3M、200GB，约 40 元/月）；如实际规格不同，不改变架构。
- 前端使用 React + Vite + Tailwind + ECharts；FastAPI 继续作为后端；现有 Jinja 模板保留为迁移兼容页。
- 数据库继续 SQLite；新增规范化表并回填稳定 `item_id`；不得破坏现有日报快照。

### LLM

- 使用 DeepSeek 官方 API：`base_url=https://api.deepseek.com`，`model=deepseek-v4-flash`。
- 实现 `LLMClient`，简化 provider 后续切换；API Key 只放 `.env`/服务器环境变量。
- 日报生成时批量生成新闻、AI 要事、GitHub 项目条目的 1–3 句中文简介；失败标记 `not_generated`，不阻断日报。
- 网页问答和企业微信问答复用同一服务；回答必须附来源 URL 或来源标识。
- 默认限制：每日合计 300 次、每分钟 10 次；连续失败 3 次后熔断并持久化状态。
- 问答会话保留最近 7 天或最近 50 条，不做长期记忆。

### 企业微信智能机器人

- 现有“日报”是群机器人 Webhook，只支持发送消息；保留它用于日报推送、极端天气预警推送和显式 @ 提醒。
- 新建企业微信智能机器人，显示名建议“日报助手”，采用长连接模式，使用官方 `wecom-aibot-python-sdk`。
- 智能机器人接收群聊 `@` 提问，调用共享 LLM 问答服务，并处理消息去重、心跳、断线重连、频率限制。
- 智能机器人官方不支持 @ 群成员，因此需要显式 @ 时由现有 Webhook 补发；提醒映射依赖企业微信 userid/手机号，需在实现前做真实环境验证。
- 长连接与现有 Webhook 属于两个能力，不能互换。

### 极端天气预警

- 配置单一主地区，数据模型预留多地区。
- 使用免费公开源轮询：主源为中央气象台/中国天气网公开数据，备用源为和风天气免费 API；每 10 分钟一次。
- 预警作为独立事件记录与推送，不改动当日日报快照。
- 推送渠道：PushPlus 优先，企业微信 Webhook 备用。
- 预警首次发布和等级升级时推送；降级/解除只更新网页时间线，不推送。
- 天气页展示首次、升级、降级、解除的时间线，并标记数据源与降级状态。
- 当前公开源无 SLA，需实现解析失败暂停、去重和备用源切换。

### 收藏与数据可视化

- 收藏对象仅限新闻、AI 要事、GitHub 项目条目；支持备注；重复收藏幂等。
- 可视化只做新闻热词和 GitHub 热度，不做天气趋势图。
- 新闻热词使用中文分词 + 停用词，按日报日期统计 Top 10；GitHub 以 `owner/repo` 为主键展示每日 star、新增量和上榜次数。
- 图表默认最近 7 天，可切换 30 天；优先读取历史快照/趋势快照，不直接实时请求外部源。

### 数据保留

- 日报、趋势、预警默认保留 180 天，可配置。
- 收藏和备注永久保留。
- 问答会话保留 7 天，由每日清理任务自动删除过期会话。
